# The four libraries `npm audit` cannot see

11 Sept 2026. Raised in the round-7 security audit; this is the record the
dependency scanner structurally cannot keep.

**Updated the same day**, after Codex asked for the pdf.js flaw to be
remediated rather than argued down. pdf.js is no longer a CDN pin: it is
vendored in `vite-app/public/pdfjs` at **6.3.289**, outside both of its
arbitrary-execution advisories. The rest of this record stands.

`npm audit` reads `package.json`. Four of this app's libraries are not in it.
Three are pinned URLs fetched from `cdn.jsdelivr.net` at the moment a button
needs them; the fourth is vendored and served from this origin. No scanner in
this repo looks at any of them, and none will. `cdnPins.test.mjs` is the
substitute: it reads the pins out of the source, hashes the vendored bytes,
reads this table back, and fails when they disagree — so nothing can land
without an entry here saying what it parses and why the version is the one
we are on.

## The pins

| package | version | loaded by | reads what | bytes checked by |
|---|---|---|---|---|
| `xlsx` (SheetJS) | 0.18.5 | `cdnLibs.js` | nothing — writes only | SRI (sha384) |
| `jspdf` | 2.5.2 | `cdnLibs.js` | nothing — writes only | SRI (sha384) |
| `jspdf-autotable` | 3.8.4 | `cdnLibs.js` | nothing — writes only | SRI (sha384) |
| `pdfjs-dist` | **6.3.289**, vendored | `jobDetail.jsx` | **a PDF somebody dropped** | sha256 of both files, in `cdnPins.test.mjs` |

## The one that matters

Three of the four only ever *write*: `book_new`, `aoa_to_sheet`, `write`,
`autoTable`. The bytes going in are the app's own rows. SheetJS's known
advisories are in its **reader**, and nothing here calls `XLSX.read`, so the
frozen-at-0.18.5 problem (SheetJS left npm; that version will never be
patched there) costs this app nothing today.

pdf.js is the exception, and the only one of the four that parses a file a
person chose: `getDocument({ data: await file.arrayBuffer() })` on whatever
was dropped into Upload report, to prefill the weld numbers.

## Why the version moved, and where to

Verified against OSV on 11 Sept 2026 — the whole package, not one advisory,
because "take the latest" would have been wrong for most of the last year:

| advisory | introduced | fixed |
|---|---|---|
| CVE-2018-5158 | 0 | 1.10.100 / 2.0.550 |
| **CVE-2024-4367** | 0 | **4.2.67** |
| **CVE-2026-16633** | **5.6.83** | **6.2.108** |

Both of the live ones are arbitrary JavaScript execution on opening a
crafted PDF. Safe is `>=4.2.67 <5.6.83` **or** `>=6.2.108`. The app was on
3.11.174 — inside the first window.

**6.3.289** was chosen over the top of the lower window (5.5.207) for two
reasons:

1. **The sink is gone, not disabled.** 5.x still ships the PostScript
   function compiler — `new Function("src","srcOffset","dest","destOffset",
   compiled)` in the worker — switched off by `isEvalSupported: false`.
   6.x deleted that path, which is why `isEvalSupported` is no longer an
   option at all. Measured: `new Function(` appears once in 5.5.207's main
   build and twice in its worker; **zero times** in either of 6.3.289's.
   The one `Function(` left is core-js's `Function('return this')`
   globalThis fallback on a constant string, and `cdnPins.test.mjs` allows
   exactly that one and no other.
2. **5.x gets no more security fixes.** CVE-2026-16633 was fixed in 6.2.108
   and not backported to a 5.6.x. Staying under 5.6.83 is a window with no
   maintainer behind it; 6.x is the line a future fix will arrive on.

`isEvalSupported: false` is still passed at the call site. On 6.x it does
nothing — the test reading the bytes is the load-bearing half — and it is
there as the seatbelt for a downgrade.

## Why it is vendored rather than pinned to the CDN

3.11.174 is the last build that loads by `<script>` tag. Every build since
is **ESM only** (`.mjs`, no UMD, `legacy/` included), so the version could
not move at all while a script tag was the loader — which is the real reason
the app sat on a vulnerable build. A dynamic `import()` takes no `integrity`
attribute, so moving forward on the CDN would have meant giving up SRI.

Serving the bytes from this origin is what stands in for it, the same trade
`public/fonts` made for the webfont URL. Three things fell out of it:

- **The SRI exception is retired.** pdf.js fetched its own worker, so no
  `integrity` of ours ever rode on that request. Same-origin, there is
  nothing to attest.
- **`worker-src` narrowed to `'self'`.** `blob:` was pdf.js's alone — the
  wrapper it minted to reach a cross-origin worker (`_createCDNWrapper`).
  Same-origin, pdf.js calls `new Worker(url, { type: "module" })` directly.
  Nothing else in the app has ever made a Worker.
- **The worker's caching hazard is gone.** From the CDN the worker fetch was
  no-cors, so the response was opaque — status 0 whether it was the worker
  or a hotel wifi sign-in page — and `CacheFirst` would have filed the
  portal page under the worker's URL for a year. That is why it had a
  `NetworkFirst` route of its own. Same-origin the status is plain, so both
  files take `CacheFirst` on 200 alone.

Cost: **1.79 MB** in the repo and in `dist/`. It is kept out of the precache
(`globIgnores: ["**/pdfjs/**"]`) and fetched on the first dropped PDF, so
the install and update download is unchanged for the crew — the same bargain
it had on the CDN.

## What was verified, and what was not

Measured here, one version per process, against a three-page PDF with a text
layer, running `pdfText()`'s body verbatim:

- **Text extraction is byte-identical** across 3.11.174, 5.4.149, 5.5.207,
  6.2.108 and 6.3.289 — same sha, 410 chars, 3 pages — with and without
  `isEvalSupported: false`.
- **`doc.destroy()` is gone in 6.x.** `TypeError: doc.destroy is not a
  function` on both 6.2.108 and 6.3.289. It was in a `finally`, so a read
  that had *succeeded* would have been reported as a failure. Now
  `task.destroy()`, which works on every version from 3.x up.
- **`isEvalSupported: false` is harmless on 6.x** — ignored, identical output.
- Same-origin `workerSrc` takes the direct `new Worker(…, {type:"module"})`
  path; a Worker that fails to construct falls through to `#setupFakeWorker`
  (main-thread parsing), so a CSP mistake here degrades rather than breaks.

**Not verified in a browser.** All of the above is Node. It establishes API
compatibility and identical output; it does not establish that the module
loads, the worker starts, or the MIME type is right on a real device. The
browser check is: open Job detail → **+ Upload report**, drop a PDF with a
text layer, and confirm the weld numbers fill in, with no CSP or MIME error
in the console. Worth doing on one crew tablet as well as a desktop.

## What would change this record

- A PDF **preview** — anything that draws a page rather than reading its
  text. `cdnPins.test.mjs` fails on `.render(`, `canvasContext` or
  `getViewport(` in `jobDetail.jsx`.
- `'unsafe-eval'` in `appPolicy`, for any reason.
- `XLSX.read` anywhere, which would put SheetJS's frozen reader on the path
  of a file somebody supplied.
- A new advisory against 6.x — check OSV for the whole package, not the one
  CVE, and note that 6.x is the maintained line.
