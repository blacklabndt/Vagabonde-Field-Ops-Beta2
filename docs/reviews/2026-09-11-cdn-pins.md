# The four libraries `npm audit` cannot see

11 Sept 2026. Raised in the round-7 security audit; this is the record the
dependency scanner structurally cannot keep.

`npm audit` reads `package.json`. Four of this app's libraries are not in it
— they are pinned URLs fetched from `cdn.jsdelivr.net` at the moment a
button needs them. No scanner in this repo looks at them, and none will.
`cdnPins.test.mjs` is the substitute: it reads the pins out of the source,
reads this table back, and fails when the two disagree, so a new pin cannot
land without an entry here saying what it parses and why the version is the
one we are on.

## The pins

| package | version | loaded by | reads what | SRI |
|---|---|---|---|---|
| `xlsx` (SheetJS) | 0.18.5 | `cdnLibs.js` | nothing — writes only | yes |
| `jspdf` | 2.5.2 | `cdnLibs.js` | nothing — writes only | yes |
| `jspdf-autotable` | 3.8.4 | `cdnLibs.js` | nothing — writes only | yes |
| `pdfjs-dist` | 3.11.174 | `jobDetail.jsx` | **a PDF somebody dropped** | main yes, worker no |

## The one that matters

Three of the four only ever *write*: `book_new`, `aoa_to_sheet`, `write`,
`autoTable`. The bytes going in are the app's own rows. SheetJS's known
advisories are in its **reader**, and nothing here calls `XLSX.read`, so the
frozen-at-0.18.5 problem (SheetJS left npm; that version will never be
patched there) costs this app nothing today.

**pdf.js is the exception, and it is the only one of the four that parses a
file a person chose.** `pdfText` in `jobDetail.jsx` hands
`getDocument({ data: await file.arrayBuffer() })` whatever was dropped into
the Upload report dialog, to read the weld numbers off it.

3.11.174 predates the fix for pdf.js's arbitrary-execution flaw
(CVE-2024-4367, fixed in 4.2.67), where a crafted font in a malicious PDF
reaches a function constructor and runs in the page's own origin. Two things
keep it out of reach here, and **both are invariants nobody had written
down** — which is the actual finding:

1. **The app never renders a page.** The sink is in the display layer's glyph
   path builder, reached by drawing to a canvas. `pdfText` calls
   `getTextContent()` and nothing else. Add a PDF preview through this same
   loader and the sink is live.
2. **The app's CSP has no `'unsafe-eval'`** (`appPolicy` in `worker/csp.mjs`).
   A function built from a string does not run in this origin. Add
   `'unsafe-eval'` for anything and the sink is live.

`cdnPins.test.mjs` asserts both, so neither can be undone quietly. Neither is
a fix: they are two doors held shut, and the test is what notices if one
opens.

Staying on 3.11.174 is deliberate and recorded in the loader's own comment:
it is the last build that loads from a script tag, and 4.x is ESM-only.
Moving to 4.x is a real change to how the library is fetched, not a version
bump, and it is not worth doing while both doors are shut and tested.

## The worker has no SRI, and cannot

pdf.js fetches `pdf.worker.min.js` itself, so no `integrity` attribute of
ours is on that request. The main script is pinned by hash; the worker is
pinned by version alone. It is named as the one exception in the test rather
than left to be noticed.

## What would change this record

- A new CDN pin — the test fails until it is in the table above.
- A PDF preview, thumbnail or any call that draws a page.
- `'unsafe-eval'` appearing in `appPolicy`.
- `XLSX.read` appearing anywhere.

Any of those turns a documented non-issue back into a live one.
