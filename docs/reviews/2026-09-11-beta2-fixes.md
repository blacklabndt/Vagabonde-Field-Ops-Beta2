# Beta 2 review fixes — implementation handoff

Kyle authorized applying the five findings after Claude's review. All five

**The database migration remains a draft, not an applied migration. Nothing

## Changes

1. **F1 — tax snapshot:** nullable `tickets.gst_rate`, a service-only
   `freeze_ticket_gst` RPC, first-invoice fallback in `mark_tickets_invoiced`,
   and snapshot-aware invoice, approval, tracker/CSV and reopened-ticket
   readers. No historical backfill. Existing null rows retain the client-rate
   fallback. Zero is preserved as an exemption.
2. **F2 — precision:** `NumField`/`acceptsNumberText` accept an explicit
   decimal limit (three by default, two for rates/GST). `step=0.5` still allows
   `2.25`. Ticket and rate writes also reject excess precision, so an older
   offline payload cannot bypass the input fix. The existing half-cent
   arithmetic remains unchanged.
3. **F3 — hours:** Ask walks crew rows by unique `id` until an empty page,
   retaining caller authorization and covering reduced API caps.
4. **F4 — backup:** table reads stop on an empty page, with each request also
   bounded by the remaining part row budget. This avoids overflowing a part
   when a smaller server cap does not divide its row limit evenly.
5. **F5 — calendar dates:** ISO-shaped inputs must round-trip to the same UTC
   calendar date; February 31 is rejected before a database request.

## Two deliberate refinements to Claude's proposal

- Reserve the tax rate **before** rendering/sending, using one atomic,
  row-locked database update. Stamping it only after sending allows concurrent
  sends to email different totals. A failed email keeps the reservation for
  retry, but approval status/token/sent timestamps remain untouched until the
  existing successful-send write. Withdrawals and un-invoicing also keep it.
- Protect snapshot updates with the existing column-level UPDATE grants.
  They already exclude all service-owned approval fields. The new column is
  explicitly revoked from anon/authenticated, and a restrictive INSERT
  policy requires null on client-created tickets. A `WITH CHECK gst_rate is
  null` on updates would wrongly prevent editing a withdrawn snapshotted
  draft. The SQL role probes check both ordinary inserts and forged ones.

The aging RPC reports subtotals already; it needs no GST change. The
`search_tickets` result keeps its existing `client_gst_rate` field name so
the tracker and accounting export receive the applied rate without a
response-shape change.
