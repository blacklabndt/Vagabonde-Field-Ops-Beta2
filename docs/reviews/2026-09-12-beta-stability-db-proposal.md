## Recommended transaction boundary

Replace the existing header UPDATE, old-line SELECT, DELETE, INSERT and compensating INSERT with **one SECURITY INVOKER PostgreSQL RPC containing the header patch and complete line replacement**. A lines-only RPC closes the destructive gap but still commits changed contacts/status/delays when billing fails. Header plus lines is the proposed boundary. Crew remains a separate workflow and transaction; creation of new tickets is also outside this change. Do not claim atomicity for an entire ticket/crew save.

Suggested contract: `public.update_ticket_document(p_ticket_id text, p_patch jsonb, p_lines jsonb) returns jsonb`. Result: `{id, total, lines_replaced}`. Total is read through `tickets_read`, never directly from the base table on caller authority. Use an explicit function search path (`pg_catalog, public`) and fully qualified application objects. Revoke all function privileges from PUBLIC and anon; grant EXECUTE to authenticated only. Do not change table grants, RLS, triggers, money masking, approval credentials, GST privileges, or helper ACLs. Do not use SECURITY DEFINER to work around a failing permission probe.

Exact operation sequence, all inside the RPC's implicit transaction:

1. Require a JSON object patch with required `status`; accept only `status`, `delays`, `client_contact`, `contractor_contact`. Reject unknown keys and invalid JSON types. Require an array for `p_lines`; SQL NULL/JSON null must never mean an empty replacement. Keep omitted optional patch keys distinct from explicit JSON null and empty text. Status remains validated by the existing status constraint, with the existing refusal rules below; do not silently narrow or broaden the current transition matrix.
2. Select only granted ticket metadata (`id`, `job_id`, `status`, `approved_at`) from `public.tickets WHERE id=p_ticket_id FOR UPDATE` into explicit variables, not `%ROWTYPE`/`SELECT *`. No row means an error, never success. This lock serializes the new RPC with another invocation and ticket status UPDATEs. Under READ COMMITTED a waiter must use the row values obtained after acquiring its lock.
3. Check the job via the caller-visible jobs row and reject `Complete`, matching `assertJobRowOpen`. A missing/invisible job is a failure, not permission to proceed. Keep the existing client preflight for its explanatory messages. For this bounded fix do not add a job row lock: it would require checking jobs UPDATE privileges and reviewing job-delete/archive lock order. Consequently this is a server recheck, not a claim that concurrent job completion is serialized.
4. Reject approved_at non-null and statuses Approved/Invoiced. Reject current Awaiting approval plus requested Draft using a stable machine-readable error marker. This must happen before the header changes. Map that marker to the existing `sentForApproval` flag so outbox replay still writes permitted crew hours. Preserve existing `ticketGone`, session-expiry and ownership diagnostics for not-found/zero-update cases; never infer ownership from every RPC failure.
5. UPDATE only the four patchable header columns, using JSON key presence to choose existing values versus explicit replacements; never put total, GST, approval or invoice fields in the target list. Use `RETURNING id` and fail unless exactly one row changed. An RLS-denied UPDATE can otherwise silently affect zero rows. RLS remains authoritative for own-ticket/Admin/Coordinator header access.
6. Determine price capability with the existing authoritative `private.user_role()` and fail-closed NULL handling. For Admin/Technician, require `private.can_write_ticket(p_ticket_id) IS TRUE` before touching lines; use the existing policies as well. For other roles permitted to change this header, skip billing and return `lines_replaced=false` with masked total. This makes the current comment's metadata-only intent explicit even for zero-valued tickets: the current `oldLines.length === 0 && row.total > 0` heuristic does not work with a masked null total. Claude must explicitly agree to this branch as part of workflow preservation; do not pretend the old implementation already handles all these cases correctly.
7. For a billing writer, validate every line and then DELETE all lines for the locked ticket and INSERT the replacement within this transaction. Use explicit insert columns `ticket_id,kind,label,unit,quantity,unit_rate,line_order`; ticket_id comes only from the RPC argument. Extract rows from the JSON array WITH ORDINALITY and assign line_order from that ordinality, preserving interleaved display order deterministically. Do not accept incoming IDs, ticket_id, or line_order. Empty array intentionally deletes all lines and results in zero total, preserving saveable blank drafts.
8. Numeric validation: kind is weld/charge; label is a JSON string (retain currently allowed empty labels), unit is string/null; quantity and unit_rate are finite, nonnegative JSON numbers. Reject booleans, strings, NaN/infinity and missing values. Use PostgreSQL numeric arithmetic, preserve arbitrary existing fractional rate precision, and calculate the sum of per-line rounded cents, not rounding only the grand total. Reject a total over 99999999.99. Preserve existing quantity/rate semantics after `cleanLine`; do not introduce a two-decimal limit that prevents legacy rate lines from saving. Existing NOT NULL/check constraints, cents trigger and balance constraint stay active. Any insert/trigger/constraint failure must escape the function and roll back the header and DELETE. No exception handler may swallow it or try a separate restoration.
9. Return the masked total from `tickets_read` and `lines_replaced`. On confirmed success only, `Db.updateTicket` updates its remembered fingerprint parts and returns its compatible `{id,total}` result. If `lines_replaced=false`, do not remember submitted lines as server data. Keep client cleanLine/overflow preflight and friendlyLineError mapping. Never fall back to the old delete/insert implementation when the RPC is unavailable.

This is a precise implementation contract, not executable SQL. The implementation must demonstrate all steps against the actual grants and policies before being considered approved for release.

## Concurrency, retries and release limits

- A lost response after commit is ambiguous: server state is either the complete old document or the complete new one. The client must not claim rollback or launch a compensating request. Existing outbox retries may replace with the same document again; they must retain their session checks and server status checks.
- Existing queued base fingerprints are advisory overwrite detection, not a compare-and-swap token. Preserve their payloads and warnings. The ticket row lock prevents two new replacements from interleaving, but last permitted save can still overwrite an earlier committed save. Adding optimistic revisions requires a separate agreed design; the existing crew-inclusive fingerprint cannot simply become a billing-only database predicate.
- Approval UPDATEs acquire the same ticket lock. Once Awaiting approval is committed, a later queued Draft RPC refuses correctly. However `mailApproval.ts` renders/sends before a separate final token/status UPDATE. Locking this RPC alone cannot serialize that entire email workflow or a prior approval read. Approval token fingerprints remain essential; do not claim this proposal closes every approval race.
- Do not introduce a job lock without reviewing ticket/job/line ordering across delete_job, archive clear, approval and billing flows. Existing direct line writers do not acquire the ticket lock before deleting; mixing old clients and new clients is not a proof of serialization. Database deadlocks, if encountered, must abort the transaction and surface as retryable failure, never partial success.
- After both reviewers agree, SQL initially belongs in `supabase/handover/` with isolated probes, per CLAUDE.md. Apply RPC before deploying its caller; then file the actual applied migration timestamp. This is additive, so old clients remain compatible but retain the original destructive vulnerability. Require the active clients/PWA to refresh and verify the deployed caller before claiming closure for users. Revoking direct line writes or forced minimum-client enforcement is outside this fix and needs its own design, since a SECURITY INVOKER RPC relies on those grants.
