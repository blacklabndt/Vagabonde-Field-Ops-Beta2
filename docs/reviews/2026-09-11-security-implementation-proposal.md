For S4, the existing prompt already says notes are data and built-in knowledge wins. That is a useful instruction, but direct database writes bypass extraction and raw interpolation permits delimiter spoofing. Escaping delimiters alone cannot guarantee prompt-injection resistance. This finding is not a claim that a Helper gains Admin SQL access: tools still run as the victim caller, and mutations are proposed for confirmation. The demonstrable issue is persistent cross-user prompt contamination and misleading output risk.

The nominal 200-note cap is enforced in application learning code, not the INSERT policy. A staff caller can add more directly; the oldest-first LIMIT then lets older notes occupy the shared prompt window. Add a server-enforced bounded write path and test concurrent inserts. The caller must never be able to assign another author's identity or supply a privileged role.

## Claude's candidates requiring a narrower claim

**Approval recipient selection: a business control decision, not a newly demonstrated privilege bypass.** `ask/index.ts:334` uses `ticketApprovalAddress`, which prefers an email extracted from the free-text contact label (`askSends.ts:106`). But `send-ticket-approval/index.ts:35–39,69–86` already intentionally accepts caller-supplied recipients from the ticket's technician or an Admin/Coordinator. A technician can therefore direct their own approval link to an inbox they control without exploiting Ask. If the intended guarantee is independent client approval, the current workflow does not enforce it. Fixing only the regex leaves the direct send route and scheduled paths unchanged.

Proposal: use a structured client-contact reference as the default recipient, show the actual address on the confirmation, and record recipient provenance. If Kyle's intended policy requires independent client identity, permit off-directory overrides only to designated office roles with a reason and audit event, enforce this on every send/schedule/resend path, and define how existing scheduled rows are handled. Claude should confirm the intended policy from existing product decisions before calling the current flexibility a bug. Email possession still does not prove legal identity.

**Anonymous approval logging: conditional exposure, not a demonstrated unconditional flood.** `approve-ticket/index.ts:143–148` catches and logs failures before a token is established. `handle:246–284` launches settings and token reads before authorization completes. However, missing or random invalid tokens normally return a notice; they do not themselves reach the catch. A concrete attacker-controlled input that reliably throws on a healthy deployment has not been demonstrated. Database/service failures can turn repeated anonymous requests into log amplification. Proposal: quietly reject malformed/missing credentials, perform settings reads only after token validation, and aggregate/rate-limit pre-auth operational failures. Preserve operational visibility rather than dropping every database failure. Do not label random-token requests as proven arbitrary log insertion.

## Missing features worth adding

These are risk-ranked proposals, not claims about unseen production configuration.

| Control | What it would catch or prevent | Proposed acceptance condition |
| --- | --- | --- |
| Distributed abuse and spend budgets (high) | Repeated authenticated Ask calls, memory insert flooding, mail bursts and push subscription growth. Frontend throttling is bypassable. | Direct function/RPC calls hit atomic per-user and project limits; parallel requests cannot overspend reservations; return 429 with retry information; charge actual usage and expire abandoned reservations. Start with Ask and memory writes. |
| Stronger authentication for privileged operations (high) | A stolen Admin password/session being used for account changes or restore. No explicit AAL2/MFA check was found in inspected privileged handlers; hosted configuration was not inspected. | Inspect existing Auth settings first. Then enforce fresh stronger authentication at server-side sensitive operations, with enrollment/recovery and a tested emergency-access process. Do not lock out the only Admin during rollout. |
| Security audit events and alerts (high) | Silent account unlocks, role changes, backup disconnects/restores, unusual approval recipients and quota abuse. `audit_log` exists, but presence of a table does not establish coverage. | Inventory current events; write missing security events server-side with actor, target, outcome, time, correlation ID. Ordinary clients cannot rewrite authoritative events. Alert on defined unusual events without including tokens or unnecessary personal data. |
| Shared-memory management and safety tests (medium) | Persistent poisoned guidance affecting colleagues and stale notes surviving changes. | Keep automatic learning as previously requested; show provenance and allow Admin quarantine/delete, bounded storage, and a shared-memory off switch. ## Proposed implementation sequence — awaiting agreement

1. **Authorization fix:** S1, a shared guard and negative tests across every affected route. Avoid unrelated UI redesign.
2. **Ask boundaries:** S4/S5/S6 together: untrusted memory handling, bounded DB writes, request size/schema checks, atomic quotas, deadlines, and safe error responses. Preserve automatic learning; do not introduce mandatory note approval without a product decision.
3. **OAuth and push:** single-winner state consumption plus bounded, validated push registration/dispatch. Establish supported push providers before choosing an allowlist.
4. **Privileged-operation protection:** verify hosted MFA settings, then implement agreed step-up authentication and missing security-event coverage.
5. **Approval policy changes:** only after the recipient/receipt requirements are settled; enforce centrally across interactive, Ask, scheduled and reminder paths.

Suggested starting limits for discussion, not agreed production values: Ask JSON 128 KiB, at most 24 input turns of 4,000 characters each, one in-flight Ask request per user, and a configurable short-window per-user quota plus a project daily spend ceiling. Measure serialized size and existing client history before fixing these numbers. A quota-store failure must stop new paid work with a retryable response; release concurrency leases on failure and expire them after crashes. Browser-side history limits must match server-side acceptance.
